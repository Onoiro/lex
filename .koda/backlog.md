# BACKLOG — подготовка Lex к публикации в маркетплейсах

Контекст: подготовка к размещению в RuStore (первый маркетплейс) и открытому доступу.
Экономика и тарифная модель обсуждены (см. историю чата от 03.09.2026): Free 500 симв.
перевода/день + 500 симв. TTS/день (как в текущих лимитах), Pro ~99 ₽/мес. Тарификация —
по символам, только «дорогие» облачные операции (перевод, TTS). Словарь/примеры бесплатны
(queryCorpus без API-ключа). TTS остаётся на API v1 (тарификация за символы, в ~18 раз
дешевле v3 для коротких слов). Финальные лимиты тюнятся по телеметрии затрат (B-12).

Правила работы с бэклогом:
- Задачи берутся по порядку приоритета (P0 → P3), если пользователь не сказал иное.
- Перед реализацией задачи — составить детальный план в `.koda/plans/<имя>.md`.
- После реализации — обновить этот файл (статус, дата, коммит) и KODA.md.

## P0 — до публикации в RuStore / открытом доступе

### B-1. Глобальный дневной бюджет прокси (финансовый предохранитель)
**Статус:** done (2026-09-08)
**Зачем:** единственная защита, которая гарантированно останавливает траты. Защита не
от одного злоумышленника, а от финансового риска в принципе (в т.ч. баги, вирусный
всплеск, ботнет).
**Что сделано:**
- Класс `GlobalBudget` в `proxy/security/quota.py` — глобальный счётчик символов/день
  на ВСЕХ пользователей суммарно (translate + tts вместе), окно UTC, in-memory.
- При превышении → 503 `{"error": "service_overloaded"}`.
- Лимит через env var `GLOBAL_DAILY_CHAR_LIMIT`, дефолт 300 000 символов/день
  (~390 ₽/день затрат Yandex API).
- Кэшированные ответы не расходуют глобальный бюджет (кэш проверяется до списания;
  для translate добавлен хелпер `get_cached_translation` в translator.py).
**Критерии готовности:** pytest-тесты на исчерпание/сброс бюджета; 503 при превышении;
лимит настраивается без пересборки образа. ✅

### B-2. CORS whitelist + X-App-Token
**Статус:** done (2026-09-08)
**Зачем:** сейчас `allow_origins=["*"]` — любой сайт может дёргать прокси из браузера
посетителя. Токен отсекает ~99% скрипт-киди (не защита от целевой атаки — квоты и
бюджет остаются настоящей защитой).
**Что сделано:**
- Класс `AppTokenAuth` в `proxy/security/token_auth.py`; env `APP_TOKENS`
  (список через запятую, ротация). Пустой `APP_TOKENS` = проверка выключена
  (обратная совместимость при выкате). Без токена → 403 `{"error": "unauthorized"}`.
  `GET /` (health-check) и OPTIONS preflight — без токена.
- CORS whitelist через env `ALLOWED_ORIGINS`; дефолт: `https://lex.2-way.ru`,
  `https://localhost` (Capacitor Android), `capacitor://localhost` (iOS),
  `http://tauri.localhost` (Tauri Win/Linux), `tauri://localhost` (Tauri macOS).
- Клиент: `proxyClient.ts` с `proxyHeaders()`; все 4 сервиса шлют `X-App-Token`
  из `VITE_APP_TOKEN` (build-time env).
- Порядок выката: прокси без APP_TOKENS → релиз клиента с токеном → включить
  APP_TOKENS на сервере. Старые APK без обновления сломаются на шаге 3 —
  компромисс до B-3 (version gate).
**Критерии готовности:** запрос без токена → 403; запрос с чужим Origin → блокировка
CORS; тесты; клиент работает на всех 3 платформах. ✅ (172 pytest, 293 vitest)
**Примечание:** фактические origin'ы Capacitor/Tauri стоит сверить в DevTools
при следующей сборке под платформу.

### B-3. Минимальная версия клиента (client version gate)
**Статус:** done (2026-09-10)
**Зачем:** без этого нельзя ни ротировать токены, ни менять API, ни заставить
устаревшие клиенты обновиться. Обязательная инфраструктура перед любыми ломающими
изменениями.
**Что сделано:**
- Клиент шлёт версию приложения в заголовке `X-App-Version` (semver, инжектится
  при сборке из `client/package.json` через `define` в vite/vitest конфигах).
- Прокси: класс `VersionGate` в `proxy/security/version_gate.py`, env
  `MIN_APP_VERSION`. Пустой/не заданный = проверка выключена (обратная
  совместимость, тот же паттерн выката, что у APP_TOKENS).
- Версия ниже/отсутствует/невалидна → 426 `{"error": "update_required",
  "min_version": "..."}`. Клиент показывает полноэкранную заглушку
  «Обновите приложение» (`components/UpdateScreen.tsx`, i18n `update.*`)
  с кнопкой «Перезагрузить» (PWA) и ссылкой на магазин/загрузку
  (Android: `VITE_RUSTORE_URL`, web/desktop: `VITE_DOWNLOAD_URL`).
- Порядок выката: прокси без MIN_APP_VERSION → релиз клиента с заголовком →
  установить MIN_APP_VERSION на сервере.
**Критерии готовности:** старая версия получает понятный ответ; тесты. ✅
(193 pytest, 299 vitest)

## P1 — до включения биллинга

### B-4. SQLite-кэши + Docker volume (персистентность)
**Статус:** todo
**Зачем:** все 3 кэша (переводы 7д, TTS 500 записей, словарь 30д) сейчас in-memory —
каждый рестарт контейнера = повторные траты на те же слова от всех пользователей.
Цель: слово «hello» переводится через API Яндекса 1 раз за историю сервера.
**Что делать:**
- Заменить in-memory кэши на SQLite (не Redis: меньше инфраструктуры, нагрузка
  копеечная). Файл БД в volume.
- Добавить volume в docker-compose.yml (сейчас его нет вообще).
- Серверный TTS-кэш нужен несмотря на клиентский Cache API (переустановка
  приложения, новое устройство, веб).
**Критерии готовности:** рестарт контейнера не сбрасывает кэш; тесты; размер БД
контролируется (TTL-чистка).

### B-5. Device ID + персистентные квоты на устройство
**Статус:** todo
**Зачем:** квота на IP несправедлива за CGNAT мобильных операторов (сотни
пользователей = 1 IP). Device ID — база для биллинга (тариф привязан к устройству).
**Что делать:**
- Клиент: UUID генерируется один раз, хранится в localStorage, шлётся в заголовке
  `X-Device-Id`.
- Прокси: квоты на device ID (основная) + пониженный лимит на IP (антибот: много
  device ID с одного IP → срабатывает IP-лимит).
- Отсутствие заголовка → сильно урезанная квота на IP (или отказ).
- Квоты персистентные (SQLite, вместе с B-4).
- Упомянуть device ID в Политике конфиденциальности (не персональные данные, но
  прозрачность обязательна для RuStore).
**Критерии готовности:** квота следует за устройством, а не за IP; тесты; политика
обновлена.

### B-6. Эндпоинт остатка квоты + UI индикатор
**Статус:** todo
**Зачем:** прозрачность лимитов снижает раздражение; нужен для биллинга (показывать
тариф и остаток).
**Что делать:**
- `GET /quota` → остаток символов перевода/TTS на сегодня для этого device ID.
- Клиент: индикатор остатка (в Настройках / при исчерпании — понятный экран).
**Критерии готовности:** пользователь видит остаток до исчерпания лимита.

**Статус:** todo
**Зачем:** монетизация. Client-side проверку покупок обойдут.
**Что делать:**
- RuStore Purchase Validation API на прокси: покупка валидируется сервером → прокси

- Pro-статус персистентный (SQLite), с периодической перепроверкой подписки.

**Критерии готовности:** покупка в RuStore поднимает Pro на прокси; отмена подписки

## Источники решений (кратко)
- Экономика: себестоимость среднего пользователя ~2–13 ₽/мес; сценарий «текст на
  1000 слов» = ~8 ₽ за запрос; TTS v1 в ~18 раз дешевле v3 для коротких слов.
- Защита строится слоями: токен/CORS (отсеять шум) → квоты device/IP (справедливость)
  → глобальный бюджет (гарантированный стоп) → уведомления YC (информирование).
- Best practices: дневные лимиты вместо месячных; device ID без регистрации для Free;
  server-side валидация покупок; graceful degradation при исчерпании лимитов.
